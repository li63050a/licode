# 05 · 认证与登录

> 实现：`cmd/auth.go`。默认（未设置密码）**无需登录**。

## 1. 启用条件
- 设置了密码（`--password` 或 `LICODE_PASSWORD`）→ 登录启用。
- 用户名默认 `licode`（`--username` / `LICODE_USERNAME` 可改）。
- 未启用：所有页面/API 直接放行；`GET /login` 302 → `/`。

## 2. Cookie 与会话令牌（`cmd/auth.go`）

| 项 | 值 |
| --- | --- |
| Cookie 名 | `licode_auth` |
| 属性 | `HttpOnly; SameSite=Lax; Path=/; Max-Age=604800`（7 天） |
| Token 结构 | `base64url(用户名 + "." + 过期Unix时间戳 + "." + hex(hmac-sha256(secret, "user.exp")))` |
| 密钥 | `~/.licode/session.key`（持久化 → 后端重启后 cookie 仍有效） |
| CSRF cookie | `licode_csrf`（生成于登录页，`SameSite=Strict`；**validateCSRF 存在但未强制**） |

校验逻辑（`require`）：
- 无 `licode_auth` 或校验失败 → 未认证。
- 未认证且请求带 `Accept: application/json`（或路径 `/ws`）→ **401 纯文本**；否则 `302 → /login`。
- Basic Auth 辅助：`checkAuth` 存在（供远程脚本），HTTP 路由只用 cookie。

## 3. 后端登录流程（`handleLogin`）
- `POST /login`：表单 `username` + `password`。
  - 成功 → `setSession`（写 `licode_auth` cookie）+ `302 → /`。
  - 失败 → `302 → /login?error=1`（**无 cookie**）。
- `GET /login`：渲染后端自带登录页（新前端用**自己的** `/login` 页面，不走这个 HTML）。

## 4. 新前端登录链路（关键：302 上的 cookie）

后端 `POST /login` 成功时通过 **302 + `Set-Cookie: licode_auth`** 登录。`$fetch`/`fetch` 跟随重定向后会丢失 302 上的 `Set-Cookie`，因此有两种解决形态：

### 形态 A：Node 代理/中继（dev / `.output`）→ `/signin`

```
浏览器 /login 页
  → POST /signin（Nuxt 服务端路由 server/routes/signin.post.ts）
     ├─ 用 Node http.request 直连 后端 /login（不跟随 302！）
     ├─ 读取 302 响应的 Set-Cookie（licode_auth=...）
     ├─ 原样 appendHeader 回传给浏览器（浏览器 cookie 落在【前端 origin】）
     └─ 返回 {ok:true} / {ok:false,error}
  → navigateTo('/')
```

> **为什么不能用 `$fetch`/`fetch` 跟随重定向**：fetch 跟随 302 后只能看到最终响应头，302 上的 `Set-Cookie` 会丢失 → 登录「成功」但浏览器没有 cookie → `/api` 401、WS 401，后端日志永远没有「客户端已连接」。这是历史 bug 的根因（已修复，见 ops-guide §7）。

`signin.post.ts` 要点：
```ts
import http from 'node:http'; import https from 'node:https'
const backend = process.env.LICODE_BACKEND || 'http://127.0.0.1:8080'
// lib.request({..., path:'/login', headers:{'content-type':'application/x-www-form-urlencoded'}})
// res.headers['set-cookie'] 里找 licode_auth=...
// 找到 → appendHeader(event,'set-cookie',c) 逐条回传；resolve({ok:true})
// 没找到 → resolve({ok:false,error:'用户名或密码错误'})
```
- 后端是 https 时自动用 `https` 模块（按 backend 协议选择）。
- 错误（连不上后端）→ `{ok:false,error}` → 前端展示。

### 形态 B：静态内嵌（`go:embed` 单二进制）→ 原生 form `POST /login`

静态产物**不含** `server/routes/signin.post.ts`，`login.vue` 用原生表单直接提交到后端同源 `/login`：

```vue
<form action="/login" method="post">
  <input type="hidden" name="username" :value="username" />
  <input type="hidden" name="password" :value="password" />
  ...
</form>
```

- 浏览器**原生 form 提交**会跟随 302 并自动保存 `Set-Cookie`，恰好避开 fetch 跟随重定向丢 cookie 的坑，且不需要 Node 中转。
- 成功 → 302 `/` → Nuxt 主页；失败 → 302 `/login?error=1`，`login.vue` 读 `route.query.error` 显示「用户名或密码错误」。

## 5. WS 认证与 cookie 转发
- 浏览器升级 `ws://<前端>/ws` 会自动带上前端 origin 的 `licode_auth` cookie。
- 中继 `server/routes/ws.get.ts` 在 `open(peer)` 里读取 `peer.request.headers.cookie`，原样作为后端 WS 客户端的 `headers.Cookie` → 后端才能通过认证。
- 后端 Origin 校验放行，无需转发 Origin。

## 6. 前端登录守卫（`pages/index.vue` onMounted）
```
GET /api/auth
 ├─ 失败（后端不可达）→ 继续渲染界面，靠 ConnectionBanner + WS 自动重连
 ├─ enabled=false → 直接 connect()（无需登录）
 └─ enabled=true → GET /api/version
      ├─ 200 → connect()（已登录）
      └─ 401 → navigateTo('/login')
```
- 登录页 `login.vue`：用户名**预填 `licode`**；提交走 `/signin`（Node 形态）或原生 form `POST /login`（静态内嵌形态，见 §4 形态 B）；ok → `navigateTo('/')`；失败显示红色错误框（静态内嵌下经 `?error=1`）。

## 7. 跨域/跨端口说明（易踩坑）

**Node 形态**：登录 cookie 落在**前端 origin**（如 `localhost:3000`），**不是**后端 origin（`127.0.0.1:8080`）。浏览器不会把 cookie 自动带给后端；一切靠**前端代理/中继透传**（REST 代理自动带 cookie；WS 由中继手动转发 cookie）。不要试图让浏览器直连后端 `/ws` 或 `/api`（会 401）。

**静态内嵌形态**：页面与后端**同源**，cookie 直接落在后端 origin，浏览器自动携带，`/api` 与 `/ws` 天然命中，无上述问题（见 [13-静态生成与内嵌Go后端](13-静态生成与内嵌Go后端.md)）。
